# Platforms

labhq runs where Python 3.12 and `uv` run. How well each platform is supported follows plan
§9 and ADR 0003.

| Platform | Support |
|---|---|
| Linux | Official |
| macOS | Official |
| Windows through WSL2 or Docker Desktop | Official |
| Native Windows | Best effort, tested in the CI matrix |

The `Platforms` workflow (`.github/workflows/platforms.yml`) runs the whole test suite on
`ubuntu-latest`, `macos-latest` and `windows-latest` on every push and pull request.

## Windows

The official route on Windows is WSL2 or Docker Desktop: inside them labhq is on Linux and
every feature works. Native Windows works too, with the limitations listed below.

Install `uv` with the PowerShell one-liner:

```powershell
powershell -ExecutionPolicy ByPass -c "irm https://astral.sh/uv/install.ps1 | iex"
```

or with `winget`:

```powershell
winget install --id=astral-sh.uv -e
```

Then, as on any platform:

```powershell
uv tool install labhq
```

### How runs are stopped

POSIX has signals and process groups; Windows has neither in that sense. Process
termination sits behind one interface per platform (`labhq.scheduler.termination`). On
native Windows a run starts in a new process group (`CREATE_NEW_PROCESS_GROUP`) and is
stopped with `taskkill /T`, which asks the whole tree to close, then `taskkill /T /F`, which
ends it. Console processes usually refuse the polite request, so stopping a run on Windows
in practice means the forced one.

### Native Windows limitations

- The `tmux` adapter does not run on native Windows (ADR 0003). There, only the SDK adapter
  is available.
- The tests below are known to fail on native Windows. Each carries
  `@pytest.mark.posix_only("reason")`, which turns into `xfail(strict=True)` there and has no
  effect on Linux and macOS. A marked test that starts passing fails the job, so the mark
  has to go. Tests are never skipped.

The table is generated from the markers by `uv run python -m tools.platform_limits --write`,
and CI fails when it does not match them.
